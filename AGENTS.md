# Project 3: AI Provider Outage Test

- Work only in this repository's root directory (resolve with `git rev-parse --show-toplevel`). Never touch another project or repository. The external pytest temporary directory named below is the sole filesystem exception.
- Never commit, push, merge, create or switch branches, or perform any GitHub operation unless the current task prompt contains an explicit authorisation for that exact action. Read-only Git commands (`status`, `log`, `diff`, `show`, `ls-files`, `merge-base`) are always allowed.

The only network traffic permitted is (a) loopback connections to `127.0.0.1` between this project's own processes and (b) installing the specific packages the task names from the standard Python package index (or running a dependency vulnerability check when the task explicitly allows it). Never use `sudo`.
- Before running any Python tool, run `source scripts/env.sh` so the project's `.venv` is active and `TMPDIR` and `PIP_CACHE_DIR` point into the project directory, never `/tmp`. If `which python` does not point into this project's `.venv`, stop and report.

That sibling directory is outside the Git repository, on the main disk, and is the only permitted filesystem exception. Never use the repository or official evidence as pytest temporary storage.
- Keep changes small and restricted to the exact files named in each task prompt. If a file you need is not listed, or anything is unclear, stop and ask. Never "tidy", rename, reformat or refactor files that are not listed.
- Write the smallest correct solution. Do not add features, options, abstractions, helper layers, files or dependencies that the task does not list. Prefer the standard library and plain functions. No dead code, duplicated logic, commented-out code or speculative generality. Keep functions short (about 40 lines) and modules small (about 400 lines) and stay within the line budget given in the task. In every report, say what could be deleted or shortened without losing a requirement or a test.

Do not add features, scenarios, mechanisms or experiments without approval.
- If a command may run longer than a few minutes (pilot or official runs), run it inside `tmux` with output teed to a log file under `logs/`, and report where the log is. Never leave stray background processes: confirm that provider and runner processes have exited before finishing.
